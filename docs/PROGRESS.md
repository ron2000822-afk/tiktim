## 2026-11-02 — Build/deploy reliability: CI config bug + flaky Vercel build

The owner reported repeated GitHub "CI failed" emails and a failed Vercel production deployment right after the Tier 3 connector commit landed. Investigated both — neither was related to the connector work itself.

**CI failure — deterministic, fixed:** `ci.yml`'s `pnpm/action-setup@v4` step was failing instantly (before checkout, install, or any of our code ran) because `package.json` already declares `"packageManager": "pnpm@10.16.1"` and the workflow *also* passed `version: 10` to the action — current `pnpm/action-setup` refuses to run when both are set ("multiple versions specified"). Confirmed via the GitHub Actions API (job steps showed every step after `pnpm/action-setup` as `skipped`). Removed the redundant `version:` from both `ci.yml` and `ingest.yml`. Verified: CI went green on the next push.

**Vercel build failure — misdiagnosed once, then fixed for real from the actual log.** First pass: reproduced a *different*, genuine issue locally (`turbo run build` from a clean install intermittently failing `/music` and the other 5 `"use cache"` pages with *"A 'use cache' function took too long during prerendering"*, root-caused to the Postgres client's default pool size of 10 colliding with concurrent build workers) and shipped a pool-size cap for it. That fix was real and worth keeping, but it was **not** what was actually breaking Vercel — local reproduction via `.env.local` doesn't exercise the mechanism that was really failing, so the "fix" address a symptom I could see, not the actual cause. Once the owner pasted the real Vercel build log, the true cause was immediately obvious: `turbo.json` had no `globalEnv` declaration, and Vercel's Turborepo integration (remote caching enabled, unlike local runs) only passes through environment variables explicitly declared there — `DATABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` were being silently stripped before `next build` ran, even though both were correctly set in Vercel's project settings, crashing `packages/db/src/client.ts` at module evaluation. Fixed by adding a `globalEnv` array to `turbo.json` listing every var from `.env.example`, so this can't recur as new env vars are added in later phases (Resend, PostHog, Sentry).

**Lesson:** when a deploy failure is reported without logs, ask for the actual log before trusting a local reproduction — a plausible-looking local failure in the same feature area can be a real-but-irrelevant bug that burns time while the actual cause sits unexamined.

**Explicitly deferred, not attempted:** Kupat Tel Aviv, Barby, and similar sites need client-side JS execution to see any real content (confirmed live — their server-rendered HTML is an empty shell or loading skeleton). A real connector for those needs Playwright-based rendering, which is a new runtime dependency for `packages/ingest` — per CLAUDE.md's "ask before deviating from the stack" rule, that's a decision for the owner, not something to add silently. Full 9-source coverage from `docs/INGESTION.md`'s list remains a later iteration.

**Found while debugging Vercel (not yet fixed, owner is getting the connection string):** `DATABASE_URL` uses Supabase's direct connection host, which resolves to an IPv6 address Vercel's build environment can't reach (`ENETUNREACH`). Supabase's own fix for exactly this is the connection pooler (Project Settings → Database → "Connection pooling" in the dashboard) — IPv4-compatible, built for serverless/ephemeral-build use. Needs the owner to paste the pooler connection string (not something to guess or change unilaterally — it's a live credential). Tracked in memory (`vercel_pooler_migration_pending`) so this isn't lost across sessions. ## 2026-11-03 — Critical security fix: `/admin/*` was serving cached, unauthenticated 200s in production

While re-verifying the Lighthouse fix above against the live site, `curl -sI https://tiktim-xi.vercel.app/admin` showed `HTTP/2 200` with `x-vercel-cache: PRERENDER` / `x-nextjs-prerender: 1`, and the response body contained the real admin dashboard HTML ("לוח בקרה") — meaning **every unauthenticated visitor to every `/admin/*` route, and to `/search`, `/event/[slug]`, `/artist/[slug]`, `/venue/[slug]`, `/city/[city]`, `/date/[date]`, and `/music/[genre]`, was being served one cached response with no auth check at all** (`vary` had no `cookie`). This had been live and latent since Phase 2 — not caused by anything in this session, just never caught because local `next start` happened to behave correctly and masked it.

**Root cause, found by reading Next's own source rather than guessing:** this codebase's standing convention, `export const instant = false`, does **not** force per-request dynamic rendering. It only tells Next's Cache Components build-time analysis "this route is allowed to block instead of requiring a Suspense boundary around dynamic data access" — a real, documented option (confirmed directly from Next's own build error text: `[block] Set 'export const instant = false' to allow a blocking route`), but it is not itself a request-scoped dynamic signal. Without an explicit one, Next's static analysis apparently didn't trace the dynamic signal buried inside the Supabase SSR client's `cookies()` call closely enough to treat these routes as always-dynamic in production. The correct, documented API for "this must only run on a real request" is `await connection()` from `"next/server"`.

Added `await connection()` as the first line of all 18 affected route components (`/admin` layout + every admin subpage, `/search`, `/event/[slug]`, `/artist/[slug]`, `/venue/[slug]`, `/city/[city]`, `/date/[date]`, `/music/[genre]`, `/music/[genre]/[city]`), keeping `instant = false` alongside it (removing it broke the build — Next's Cache Components requires one of Suspense/`"use cache"`/`instant = false` for any route that accesses dynamic data without streaming).

**That fix was necessary but not sufficient — found a second, deeper bug while verifying it.** After rebuilding, `curl` against a real `next start` production server showed `/admin` now returning `HTTP 200` (not a redirect) with the **actual dashboard data embedded in the response body** (real event/artist/venue counts), while `x-nextjs-postponed: 1` was present. Root cause: under Next 16's Cache Components/PPR streaming, a `redirect()` thrown from an async Server Component (here, the admin layout's auth check) does not reliably stop sibling/child async components from executing — React can schedule the layout's auth check and the page's own data fetch concurrently, and if the page's query resolves and streams before the layout's redirect is fully processed, the initial HTTP response is already a `200` and the redirect gets downgraded to a `NEXT_REDIRECT` instruction embedded in the RSC payload instead of a real HTTP 3xx. A real browser's React runtime processes that instruction and navigates away (which is why Playwright's e2e test and ordinary users were never affected), but any raw HTTP client — curl, a scraper, a search engine crawler — sees a `200` with the real private data already in the response body.

**The actual, complete fix: moved the auth gate into `proxy.ts` (Next 16's renamed `middleware.ts`), which already existed in this codebase for Supabase session-cookie refresh.** Added a check there — for any `/admin/*` path except `/admin/login`, `/admin/sign-out`, `/auth/callback` — that calls `supabase.auth.getUser()` and returns a real `NextResponse.redirect(..., 307)` to `/admin/login` if the user is missing or not in `isAdminEmail`'s allowlist, entirely before any React rendering starts. This is the architecturally correct place for an auth gate: a layer that runs synchronously ahead of rendering can't race against component scheduling the way a layout-level `redirect()` can. The admin layout's own `redirect()`/denied-page checks are kept as defense-in-depth, not removed.

**Verified against a real production build (`next build` + `next start`), not just dev:**
- `curl` against `/admin` and `/admin/events` with no cookies: real `HTTP/1.1 307 Temporary Redirect`, `location: /admin/login`, empty body — no dashboard data anywhere in the response.
- `/search` still returns `200` (correct — it's public, no auth gate needed) and genuinely varies per query (`?city=tel-aviv` vs `?city=haifa` produce different bodies) — not a stale cached response.
- Full `pnpm test:e2e` (6 specs) passes; the admin-redirect test dropped from ~3.5s to ~270ms, consistent with the redirect now happening at the proxy layer instead of after RSC streaming.
- `pnpm --filter web typecheck` and `pnpm --filter web lint` both clean.

**A related, lower-severity finding flagged but not fixed this pass:** the exact same "`redirect()` downgrades to a client-only RSC instruction under PPR streaming" mechanism also affects `/event/[slug]`'s canonical-slug redirect — a wrong-slug URL variant returns `HTTP 200` (with the correct canonical URL only reachable via client-side navigation) instead of a real `307`. This has no data-leak implication (event pages are public by design), but it means search-engine crawlers may not reliably consolidate slug variants onto the canonical URL for SEO purposes. Fixing it the same way (moving the check into `proxy.ts`) would mean a DB lookup on every single event-page request at the proxy layer — a real latency/DB-load tradeoff for the site's highest-traffic page type, and `/event/[slug]` intentionally uses ISR/PPR per `CLAUDE.md`'s rendering strategy, unlike `/admin`. Left for the owner to weigh rather than decided unilaterally.

**Resolved:** pushed to `main` (commit `27b0b15`) with the owner's explicit go-ahead, confirmed CI + Vercel deploy both green, then re-verified directly against `https://tiktim-xi.vercel.app/admin`: real `HTTP/2 307` to `/admin/login`, empty body, no leaked content. The live exposure is closed.

**Two real bugs found while writing those tests, both fixed:**
1. `generateMetadata` in `/music/[genre]` and `/music/[genre]/[city]` calls `listEvents()` (defaults `dateStart` to `new Date()`) to decide the `robots: { index: false }` flag for thin pages — an "unstable value" under Cache Components that only threw once a real request hit a route needing on-demand metadata regeneration (not at build time, which is why the earlier full build never caught it). The page body already had `connection()` for the same underlying call, but that only covers the page component's own scope, not the separate `generateMetadata` function — and reusing it here would have forced the whole route from PPR (1h-revalidated shell) to fully dynamic. Fixed with `"use cache"` + `cacheLife("hours")` instead, matching the same pattern the home page already uses for the identical kind of query.
2. The search page's filter-apply button and grid/calendar view toggle links measured as small as 18-21px tall on mobile — under WCAG 2.5.8's 24px minimum touch target — and the results grid went straight from `<h1>` to the `<h3>` inside each `EventCard`, skipping a heading level. Fixed with explicit `min-h-11` on the undersized targets and a visually-hidden `<h2>תוצאות</h2>` before the grid. `/search`'s Lighthouse accessibility score went 94 → 100.

**A real performance regression found and fixed:** re-running Lighthouse mobile against the live production home page (motivated by Phase 4 mounting `AuthMenu` and `MergeLocalSaves` globally, plus `PersonalizedRail` on home) showed performance had dropped from 93 to 83 — below the ≥90 bar. Root cause, confirmed by downloading and inspecting the actual shipped JS chunk: not a single bloated dependency, but the Supabase browser client (pulled in transitively by `useCurrentUser()`) now being part of every page's critical, eagerly-hydrated bundle, when previously it was only ever used on the rarely-visited `/admin/login` page. Fixed by wrapping all three components in `next/dynamic(..., { ssr: false })` behind small Client Component wrapper files (`AuthMenuLazy`, `MergeLocalSavesLazy`, `PersonalizedRailLazy` — `ssr: false` isn't allowed directly inside a Server Component in Next 16, hence the wrappers), so their code loads in a separate chunk after the critical render path instead of blocking it. Verified the fix locally against a clean production build: total-blocking-time dropped from 330ms to 20ms, JS bootup time from 1.5s to 0.1s, and performance scores on a first clean pass were home 94, event 95, search 94, artist 97 — all clearing ≥90, with the `AuthMenu`/`MergeLocalSaves`/`PersonalizedRail` features themselves unchanged in behavior (full e2e suite, 20/20, still passes).

**Not yet fully trustworthy — local performance numbers for fully-dynamic (DB-querying) pages were noisy on repeat runs** (search measured 94 once, then 75-78 on three subsequent clean re-runs, while accessibility stayed a rock-solid 100 across all of them). Suspect this sandbox's network path to the real remote Supabase instance is slower/more variable than Vercel's deployed functions would see in production — exactly the "test the real thing, not local" lesson already learned once this session for Lighthouse specifically. ISR/PPR pages (home/event/artist) didn't show this instability, consistent with them serving a cached/streamed shell rather than depending on a live DB round-trip for every request. **This needs re-verification against the actual deployed production URL once pushed**, not more local measurement.

**One product gap noticed and flagged (not fixed — spun off as a background task):** the event detail page shows the artist's name as plain text with no link to their artist page — there was no way to navigate from an event to its artist except typing the URL directly. `event.artistSlug` is already available on the query result; just needed wrapping the heading in a `Link`, matching the existing venue-name link treatment two lines below it.
